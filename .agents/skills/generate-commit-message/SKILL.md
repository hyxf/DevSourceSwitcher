# Generate Commit Message

根据仓库中的实际改动，生成准确、简洁的 Git commit message。

## 工作流程

1. 使用只读 Git 命令查看工作区状态和差异。默认将暂存区视为本次提交内容；暂存区为空时，才根据未暂存的工作区改动生成消息。
2. 暂存区有内容时，不要把仅存在于未暂存区的改动写进提交消息。若同一文件同时有暂存和未暂存改动，以暂存区 diff 为准。
3. 如有必要，查看与目标差异直接相关的文件，理解改动目的和影响。
4. 总结主要改动，在回复中输出一条可直接复制使用的提交消息。

检查时避免读取或展示密钥、令牌、密码等敏感内容。不要为了生成消息而修改文件或 Git 状态。

如果目标差异包含多个互不相关的改动，优先建议拆分为多个提交；用户仍需要一条消息时，再概括最主要的改动，并避免声称单条消息能准确描述所有部分。

## 格式约束

- 标题遵循 Conventional Commits 结构：`<类型>(<范围>)<破坏性标记>: <描述>`。范围和破坏性标记可省略；没有明确范围时不要添加括号。
- 类型使用常见英文小写前缀，并根据改动选择：`feat`（新增功能）、`fix`（修复）、`docs`（文档）、`style`（不影响逻辑的格式调整）、`refactor`（重构）、`perf`（性能）、`test`（测试）、`build`（构建）、`ci`（持续集成）、`chore`（维护）、`revert`（回滚）。
- 范围用简短名称指出受影响的模块，例如 `api`、`ui`、`config`、`compat`、`security`；只在 diff 能支持判断时使用。
- 以 `!` 标记破坏性变更，例如 `feat(api)!: 移除旧版接口`。有必要说明迁移影响时，在正文添加 `BREAKING CHANGE:` 页脚，并用中文描述不兼容影响和迁移方式。
- 冒号后的标题描述和正文必须使用中文；产品名、库名、命令、文件名、API、代码符号，以及 Conventional Commits 的类型、scope 和 `BREAKING CHANGE` 标记可保留原文。
- 标题概括最主要改动，简短明确，不加句号；使用清晰的动作描述，例如“新增”“修复”“调整”，避免“更新代码”“修复问题”等无具体信息的泛化表述。
- 仅当改动涉及多个重要方面，或原因、影响、迁移方式需要补充说明时，才添加正文。正文与标题之间空一行，使用简短段落或条目说明，不重复标题。
- 参考格式：

  ```text
  feat: 新增功能
  feat(api): 新增 API 接口
  feat(ui): 新增用户界面
  feat(config): 新增配置项
  feat!: 引入不兼容变更
  fix: 修复错误
  fix(api): 修复 API 问题
  fix(ui): 修复界面问题
  fix(compat): 修复兼容性问题
  fix(security): 修复安全问题
  docs: 更新文档
  refactor(config): 简化配置加载流程
  perf(ui): 减少界面重复渲染
  test: 补充配置解析测试
  chore: 更新开发依赖
  feat(api)!: 移除旧版接口

  feat(config): 新增镜像源配置

  支持为不同环境设置独立镜像源，避免切换时覆盖现有配置。

  feat(api)!: 移除旧版接口

  BREAKING CHANGE: 调用方需迁移到 v2 接口。
  ```

## 操作边界

- 不将消息填入 VS Code Source Control 输入框。
- 不执行 `git add`、`git commit`、`git reset`、`git checkout` 或其他会改变 Git 状态的操作。
- 不根据文件名臆测变更目的；以 diff 和相关代码为依据。
- 如果没有可用改动，说明当前没有可总结的变更。
- 如果改动目的无法从差异中判断，简要指出不确定之处，并向用户询问必要信息，不编造原因。
